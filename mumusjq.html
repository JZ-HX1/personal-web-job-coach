注：get/indexOf 非破坏操作，多次循环取平均；insert/remove 在第 3 位对称，采用「插入后立即删除」成对计时÷2 得单次估计（保持 size 恒定）。<0.01 表示低于计时分辨率。

对照基准实测数据，可判定当前线上 App 用的是 SqList 顺序表。四条反馈逐一对应：

反馈① 拖动排序卡顿，2000 首拖不动
拖拽 = 连续大量 remove+insert。SqList 每次搬动 i 之后全部元素，单次 O(n)，连续拖拽累积卡顿。不好改
反馈② 跳到第 1 首 / 第 1500 首都瞬间
SqList get(i) 下标随机访问 O(1)，与 i 无关 → 实测 get(n−1) 始终接近 0。这正是顺序表强项 好查，也反向印证用的是顺序表。
反馈③ 第 3 首后插入，歌单越长越慢
SqList insert(3) 需把第 3 首之后 n−3 个元素整体后移，n 越大搬得越多 → 随 n 线性增长；LinkList 只走 3 步重连指针，与 n 无关 → 实测恒定。即"顺序表好查不好改，链表好改不好查"。
反馈④ 偶发闪退，日志反复越界
get/remove(i) 当 i≥size 或 i<0 时访问越界抛异常 → 必须入口做边界校验。本页所有越界操作会即时弹窗报错而非闪退。

建议

  • 读多写少、靠随机跳播（点歌、跳到第 N 首）→ 保持 SqList，get 是 O(1)。
  • 头/中部频繁插入删除（拖拽排序、插队播放）→ 用 LinkList，或拖拽时只记录意图、松手一次性 reorder。
  • 所有 get/insert/remove 入口先校验 0≤i≤size，杜绝越界闪退。
